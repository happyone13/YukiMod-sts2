# Yuki 关键词实现补充说明

## 1. 这份文档解决什么问题

这份文档补充 `docs/keyword-implementation-plan.zh-CN.md`，专门记录当前对以下问题的粗判：

- `月影` 更适合做成手牌实例，还是做成 `Power`
- `黑云 / 黑云姿态` 的真实难点在哪里
- `灵感` 的判定需要哪些技术边界
- `预见` 是否能走原版选牌与确认流程
- 表格中哪些牌效果实现起来容易返工、歧义大，或者需要先定规则

这份文档不是最终实现方案，只是先把“哪里简单、哪里危险、哪里要先定口径”写清楚。

## 1.1 当前已确认规则

以下规则已在讨论中明确，后续实现默认按这些口径推进，除非再次改口：

- `月影` 的成长按“命中”计数，不按“打出一张攻击牌”计数。
- `灵感` 可以按抽牌来源/时机区分：
  - 回合开始默认抽牌不算
  - 战斗开始后、回合进行中的抽牌可以算
- `随机（选择）` 的记录表示：未升级随机，升级后改为选择。
- 如果一张带灵感额外效果的牌不是通过“回合开始抽牌”进入手牌，则可把该牌的灵感激活状态记为 `true`。
- 当手中的灵感牌已激活时，它应使用原版手牌金光高亮逻辑。

## 2. 当前粗判

### 2.1 月影

结论：

- `月影` 应以“卡牌实例”为主，不应只做成 `Power`。
- `Power` 可以作为辅助层，但不应作为月影伤害、费用、重放次数的唯一真相来源。

原因：

- `月影` 本体就是一张会进手、会保留、会被复制、会被减费/加费、会获得重放的牌。
- 同时存在多张 `月影` 时，它们的伤害值、费用、重放次数可能不同。
- `凝聚`、复制、保留、打出时生成同复制等效果，天然都是“改某张手牌实例”。

推荐做法：

- 让 `月影` 自己保存当前伤害值。
- 让“视为月影”的牌通过单独标记参与部分效果。
- 让 `Power` 负责“攻击命中时月影+1”“回合结束时手中月影+5”这类全局广播，再由它去修改符合条件的手牌实例。

真正的难点不在“能不能检测攻击”，而在“按什么口径计数”：

- 单段攻击按命中次数算
- 多段攻击默认每个有效命中都可累计
- 群攻打到多个敌人时，默认按实际命中包累计

因为规则已经明确为“看命中”，技术上应优先看 `AfterDamageGiven`，不要只看 `AfterCardPlayed`。

这也意味着以下内容要尽量先向原版/框架对齐：

- `0` 伤害是否算命中
- 被格挡为 `0` 的伤害是否算命中
- 多段攻击、群攻、荆棘反伤等边界会不会误触发

### 2.2 黑云 / 黑云姿态

结论：

- `黑云` 本身不是难点，难点是“统一入口 + 退出例外 + 描述一致性”。
- `黑云姿态` 第一版适合先做成 `Power`，不建议一开始上重量级自定义姿态系统。

推荐拆法：

- `BlackCloudStancePower`
  - 表示“当前处于黑云姿态”
- `BlackCloudHelper`
  - 统一处理“若已在黑云，则触发额外效果，否则进入黑云”
- `BlackCloudExitGuard`
  - 处理“本次/本回合非攻击牌不会让你退出黑云”的例外

真实难点：

- 不能让每张黑云牌自己手写一套 if/else，否则后面文案和行为会漂。
- “使用非攻击牌退出黑云”是全局规则，但又有例外牌会写“保持黑云姿态”。
- 这个“保持”到底是：
  - 只对当前这张非攻击牌生效
  - 还是本回合所有非攻击牌都不退出
- 这两个规则在实现上完全不同，必须先定。

如果当前口径是“这张牌的黑云效果为：保持黑云姿态，则不会退出”，那第一版最稳的实现不是修改全局规则，而是：

- 在该牌结算前打一个“一次性忽略退出”的标记
- 当这张非攻击牌完成结算后消费掉标记

### 2.3 灵感

结论：

- `灵感` 可做，但它是当前最需要先定规约的全局机制。
- 难点不是“牌能不能进手牌”，而是“为什么进手牌”。

当前可利用的原版能力：

- `CardPileCmd.Add(..., PileType.Hand, source: ...)` 在移牌时带 `source`
- `AfterCardChangedPiles(card, oldPileType, source)` 能监听“进入手牌”
- `AfterCardDrawn(choiceContext, card, fromHandDraw)` 能单独监听“这是一次抽牌”
- `SetupPlayerTurn` 中的回合开始默认抽牌使用 `Draw(..., fromHandDraw: true)`
- 大多数战斗中途抽牌走 `Draw(..., fromHandDraw: false)`

所以技术上可以分层判断：

1. 先在 `AfterCardChangedPiles` 里抓“有牌进手”
2. 再在 `AfterCardDrawn` 里区分“这是抽牌”
3. 用 `fromHandDraw` 区分“回合开始默认抽牌”与“战斗中抽牌”
4. 对不是抽牌、但进入手牌的情况，按来源再细分

真正难点：

- 原版“抽牌”与“非抽牌加入手牌”并不是同一个语义层
- 回合开始抽牌、卡牌效果抽牌、把牌从弃牌堆拿回手、生成到手、检索到手，来源都不同
- 某些牌会写“随机（选择）一张牌触发灵感”，这不是入手事件，而是强制触发事件

目前的实现倾向：

- 对“带灵感额外效果”的牌，在进入手牌时记录一个实例级布尔值，例如 `IsInspired`
- 若来源是回合开始默认抽牌，则保持 `false`
- 若来源是战斗开始后的其他抽牌，或非抽牌进手，默认置为 `true`

这一版口径是偏玩法定义的，不是原版现成机制；但它可以稳定落在现有 Hook 上。

推荐先定一个最小来源表：

- `Draw`
- `TurnStartDraw`
- `GeneratedToHand`
- `MovedToHandFromDrawPile`
- `MovedToHandFromDiscardPile`
- `CopiedToHand`
- `ManualTrigger`

然后明确：

- 哪些来源算灵感
- 哪些来源不算灵感
- “触发灵感”与“因入手而获得灵感资格”是不是同一件事

另外需要注意：

- 有些牌效果是“直接触发灵感”，这应是单独事件，不应强行伪装成一次进手
- 有些牌是“抽一张有灵感的牌”，这里要区分“卡牌已激活”与“卡牌具有灵感词条”

### 2.4 预见

结论：

- `预见` 可以基本走原版逻辑，不需要自己做一套 UI。
- 原版有通用选牌屏，也有“多选后点确认”的流程。

当前确认到的原版能力：

- `CardSelectCmd.FromSimpleGrid(...)` 可展示一组卡进行多选
- `CardSelectorPrefs(min, max)` 当 `min != max` 时会要求手动确认
- 因此 `预见 X` 可以用“`min = 0, max = X`”来实现“可选任意数量，然后点确认”

实现建议：

- 从抽牌堆顶部取 `min(X, drawPile.Count)` 张作为候选
- 让玩家在候选里选择任意数量
- 确认后把选中的牌移入弃牌堆

需要注意：

- 抽牌堆不足时直接按现有数量展示，不应报错
- `0` 张时直接 no-op
- 文案上“查看抽牌堆顶部 X 张”与“打开整个抽牌堆”不是一回事，不能混用

## 2.5 灵感金光高亮

结论：

- 灵感牌在手里的高亮可以直接复用原版金光，不需要自定义第二套表现。

当前确认到的原版能力：

- `CardModel.ShouldGlowGold` 是原版统一入口
- 手牌容器 `NHandCardHolder` 会直接读取 `cardModel.ShouldGlowGold`
- 只要卡在手里、可打出，且当前处于 `Play` 阶段，就会走金光显示

实现建议：

- 在灵感牌基类里提供 `IsInspired` 或同义实例状态
- 让 `ShouldGlowGoldInternal => IsInspired`
- 只对“带灵感额外效果”的牌启用这条逻辑，避免所有牌都能乱亮

这样做的好处：

- 表现走原版
- 逻辑集中在卡牌实例
- 不需要额外做手牌节点补丁

## 2.6 原版可复用的“本回合限制”逻辑

结论：

- `本回合不能抽牌`：原版已有现成逻辑。
- `本回合不能获得费用`：原版也已有现成逻辑，但它的真实语义更接近“本回合不能通过能量增益效果获得额外费用”。

### 不能抽牌

原版现成实现：

- `NoDrawPower`
- 参考牌：`BattleTrance`、`BulletTime`

当前确认到的行为：

- `NoDrawPower.ShouldDraw(player, fromHandDraw)` 会阻止 `fromHandDraw == false` 的抽牌
- 但不会阻止 `fromHandDraw == true` 的回合开始默认抽牌
- 回合结束时该 `Power` 自行移除

这意味着：

- 如果牌文是“本回合不能再抽牌”，直接复用 `NoDrawPower` 很合适
- 如果牌文想连回合开始默认抽牌也封掉，那就不是原版 `NoDrawPower` 的默认语义

### 不能获得费用

原版现成实现：

- `NoEnergyGainPower`
- 参考牌：`ExpectAFight`

当前确认到的行为：

- `PlayerCmd.GainEnergy(...)` 先走 `Hook.ModifyEnergyGain(...)`
- `NoEnergyGainPower.ModifyEnergyGain(...)` 会把目标玩家本次能量增益直接改成 `0`
- 回合结束时该 `Power` 自行移除

但要特别注意：

- 它拦的是 `GainEnergy`
- 不拦每回合开始的基础回能

原因是回合开始基础能量不是走 `PlayerCmd.GainEnergy(...)`，而是：

- `CombatManager.SetupPlayerTurn(...)`
  - `ResetEnergy()`
  - 或 `AddMaxEnergyToCurrent()`

所以更准确的文案映射应是：

- “本回合不能获得额外费用”
  - 可直接复用 `NoEnergyGainPower`
- “本回合不能获得费用”
  - 需要先确认是否连回合开始基础回能也要封

如果后者也要封，就不能只靠 `NoEnergyGainPower`，还得额外介入开局回能流程。

## 2.7 卡牌实现易错点与固定口径

下面这些不是机制设计，而是已经踩过一次的实现错误。后续做卡默认按这些口径执行。

### 选牌提示文本

- 只要代码里调用了 `SelectionScreenPrompt`，就必须在 `cards.json` 中提供 `<CARD_ID>.selectionScreenPrompt`。
- 缺这个键时，运行时会直接抛 `No selection screen prompt for CARD...`，并导致玩家看到“选牌卡住”。
- 这类问题先查 `godot.log`，不要先怀疑 `CardSelectCmd.FromHand(...)` 或 `CardSelectCmd.FromSimpleGrid(...)` 本身坏了。

推荐做法：

- 参考原版 `SecretTechnique` 这类卡：
  - 代码里使用 `new CardSelectorPrefs(base.SelectionScreenPrompt, ...)`
  - 本地化里同步补 `.selectionScreenPrompt`

### 动态数值描述

- 伤害、格挡、次数、抽牌数等会升级或会被动态变量修改的文本，优先写成原版动态变量格式。
- 常用写法：
  - `{Damage:diff()}`
  - `{Block:diff()}`
  - `{Repeat:diff()}`
  - `{Cards:diff()}`
- 像“多段攻击”这类文本，不要手写固定数字再靠代码改值，否则很容易出现卡面显示不跟数值走的问题。

示例：

- 正确：`造成{Damage:diff()}点伤害{Repeat:diff()}次。`
- 错误：`造成3点伤害2次。`

### 中文文案排版

- 中文 `cards.json` 中，数值占位符与中文量词、标点默认不加空格。
- 后续录入默认采用：
  - `造成{Damage:diff()}点伤害。`
  - `抽{Cards:diff()}张牌。`
  - `获得{Block:diff()}点格挡。`

### 消耗的正确实现

- 卡牌自带关键词 `消耗`、`保留`、`固有` 默认由原版/框架自动追加到描述，不需要在效果正文重复写一遍。
- 卡牌效果中“消耗一张手牌”“消耗选中的牌”这类结算，必须优先走原版消耗方法，例如 `CardCmd.Exhaust(...)`。
- 不要自己手动把牌直接挪到某个牌堆来模拟“消耗”，否则容易绕开原版的消耗事件、动画和后续 Hook。

### 表格优先级

- `docs/yuki-card-table.xlsx` 是当前实现的第一权威来源。
- 旧的 md 草案、旧代码、旧聊天记录只能作为背景参考，不能覆盖表格。
- 如果某张牌在表格中改过效果，修卡时必须先回看 xlsx，再决定代码和本地化怎么改。

已踩过的实例：

- `神丶压制准备` 曾被按旧版本误写成带 `消耗` 的牌；后续发现表格已改为不消耗，应立即以 xlsx 为准修正。

## 3. 月影与“视为月影”的区分

这是当前必须先立的规则，否则 `凝聚` 和后续月影联动会反复返工。

至少要区分两种判断：

- `IsRealMoonshadow`
  - 指真正的 `月影` 牌实例
- `CountsAsMoonshadow`
  - 指“这张卡视为月影”的广义目标

建议不要只用一个 tag 覆盖所有场景，而是每个效果显式选择判定口径。

当前根据讨论可先采用的口径：

- “当你没有月影时生成一张月影”
  - 用 `IsRealMoonshadow`
- “手中的月影增加攻击力”
  - 默认对 `CountsAsMoonshadow` 生效
- “手中的月影获得重放 1”
  - 默认对 `CountsAsMoonshadow` 生效

仍需逐条确认的效果：

- “下次打出月影时，生成一张相同的复制”
- “回合结束时手中月影伤害增加 5”
- “如果没有月影则凝聚 1”

这些都不能靠猜，最好在正式做对应牌前明确。

## 4. 额外需要考虑的实现点

- 手满时生成到手的牌会改去弃牌堆，这种情况通常不应算 `灵感`
- 复制出的月影要不要复制当前伤害、当前费用、重放次数、临时关键词，要先定
- 回合结束时的月影成长，要不要影响弃牌堆、抽牌堆、消耗堆中的“视为月影”牌，通常不建议
- `凝聚` 的费用增加是本场永久、当回合临时，还是直到打出前持续，必须先定
- `重放 1` 是直接改 `BaseReplayCount`，还是通过临时效果层实现，决定了它会不会跨区保留
- 黑云的“保持姿态”如果未来既有“本次不退出”又有“本回合不退出”，需要两种不同标记，不能复用一个布尔值
- 灵感如果要让卡牌显示“当前已被灵感激活”，需要考虑卡牌离手再回手后是否保留该状态
- 灵感若是实例级布尔值，要确认复制、回手、洗回抽牌堆、战斗中生成复制时是否继承该值
- 任何“抽到时费用 -1”的牌都需要确认：是本战永久、仅当前实例、还是仅本次在手

## 5. 卡表粗看：高风险或高歧义牌

下面只列粗看最容易返工、最需要先定规则的牌。未命名牌先给临时代号。

### 5.1 高歧义

- `未命名-01`
  - 效果：`造成4点伤害2次；随机（选择）一张牌触发灵感。`
  - 问题：“随机”还是“选择”是两套逻辑，必须二选一。

- `未命名-02`
  - 效果：`抽一张有灵感的牌。`
  - 问题：这里的“有灵感”现在更需要区分“已经被激活的卡”还是“带灵感额外文本的卡”，语义不同。

- `未命名-03`
  - 效果：`触发手牌中灵感效果；消耗（不消耗）。`
  - 问题：这是批量强制触发，容易和“入手触发灵感”混淆，需要单独事件入口。

- `未命名-14`
  - 效果：`随机（选择）一张牌触发灵感。`
  - 问题：当前规则已明确为未升级随机、升级后选择；实现时不要再把它当成文案错误。

- `未命名-04`
  - 效果：`把手牌放到抽牌堆顶部，并抽同等数量的卡；消耗（不消耗）。`
  - 问题：放回顺序、重新抽取顺序、会不会重新抽到原牌、算不算灵感，都要先定。

- `影月`
  - 效果：`这张卡被视为月影；保留；消耗。`
  - 问题：它会直接牵动所有“月影判定口径”。

- `未命名-05`
  - 效果：`下次打出月影时，生成一张相同的复制。`
  - 问题：复制的是原始模板，还是当前实例的伤害/费用/重放状态。

### 5.2 高实现风险

- `未命名-06`
  - 效果：`把一张黑云牌从抽牌堆或弃牌堆移至手牌；黑云：保留黑云姿态。`
  - 风险：跨两个牌堆检索，外加当前非攻击牌不退出黑云的例外。

- `黑云心法`
  - 效果：`一回合内保留黑云姿态；黑云：本回合内获得2力量。`
  - 风险：这里是“本回合都不退出”，不是“当前这张不退出”，要和前者分成不同机制。

- `出鞘`
  - 效果：`进入黑云姿态，下次退出黑云姿态时获得一张[纳刀]。`
  - 风险：需要做“监听下一次退出”的延迟触发，不是单纯进姿态。

- `纳刀`
  - 效果：`本回合每释放一张攻击牌额外攻击一次；手里没有攻击牌时费用-1；消耗。`
  - 风险：同时涉及攻击计数、动态费用、当前手牌判断。

- `未命名-07`
  - 效果：`本回合每抽1张牌额外攻击一次（目前增加0）。`
  - 风险：表述还不完整，且牵涉抽牌计数与额外攻击叠加。

- `未命名-08`
  - 效果：`造成5点伤害3/4次，每次抽到时费用-1。`
  - 风险：需要稳定的“抽到时” Hook，且要定义减费持续时间。

- `未命名-15`
  - 效果：`抽一张牌，这张牌下次使用费用减少1；黑云：保留黑云姿态。`
  - 风险：这里的“这张牌”大概率指抽到的那张，不是自己；要确认抽空时是否失效，以及该减费是实例级还是一次性消耗。

- `未命名-09`
  - 效果：`抽1张牌并打出；消耗（升级后不消耗）；灵感：-1费。`
  - 风险：抽牌、自动打出、灵感减费三层时序容易冲突。

- `天际斩击`
  - 效果：`将手中所有牌放到抽牌堆顶部并抽出。`
  - 风险：和 `未命名-04` 类似，但规模更大，且更容易和手牌上限、灵感判定打架。

### 5.3 全局风险

- `神丶压制准备`
  - 效果：`抽尽可能多的攻击牌（优先灵感）。`
  - 风险：会碰到手牌上限、禁止抽牌效果，以及“优先灵感”需要稳定的流派标记入口。

- `未命名-10`
  - 效果：`每回合第一次抽满手牌时获得1费。`
  - 风险：必须明确“抽满”是指到上限，还是从未满到满；也要考虑补牌、生成到手是否算。

- `未命名-11`
  - 效果：`每花费4/3费抽1张牌。`
  - 风险：要监听“实际花费的能量”，并确认 0 费牌、减费牌、返还能量怎么结算。

- `未命名-12`
  - 效果：`获得1费，抽2张牌，本回合不能再抽牌。`
  - 风险：原版 `NoDrawPower` 可复用；仍要明确这张牌自己的抽2是否在禁止前还是禁止后。

- `未命名-13`
  - 效果：`获得2/3费，本回合不能抽牌。`
  - 风险：和上面类似，但更依赖禁止抽牌的统一规则。

- `黄昏的羁绊`
  - 效果：`固有，不能额外获得费用；回合开始时随机两张卡下次使用前费用减少1。`
  - 风险：原版 `NoEnergyGainPower` 可复用来封“额外获得费用”；但如果文案将来写成“不能获得费用”，则要确认是否也封基础回能。

## 6. 粗看下来相对容易的部分

下面这些不代表零成本，但至少不属于“先做就容易炸”的类型：

- 纯 `预见` 牌
- 单纯“黑云：额外攻击一次”的攻击牌
- 单纯“黑云：抽2”的防御牌
- `凝聚1` 进入真实 `月影` 的最小闭环
- 战斗开始 `凝聚1` 的初始遗物

## 7. 当前建议

如果下一步要实际开做，建议先落以下规则与最小实现：

1. 先定 `IsRealMoonshadow` 和 `CountsAsMoonshadow`
2. 先定黑云“保持姿态”有几种语义
3. 按 `fromHandDraw` 与进手来源把灵感来源表落下来
4. 给带灵感额外效果的牌预留 `IsInspired + ShouldGlowGoldInternal`
5. 先做 `月影 Token -> 凝聚 -> 初始遗物 -> 一张凝聚牌`
6. 再做 `预见`

不建议一开始就碰：

- 批量触发灵感
- 回手/检索/生成混合型灵感牌
- “不能额外获得费用”这类全局规则牌
- 同时改动月影、黑云、灵感三套底层
