# Yuki 关键词实现计划

## 1. 目的

这份文档基于 `docs/yuki-card-table.xlsx` 的“关键词，能力与遗物”页，以及当前 `YukiModCode` 骨架，整理友纪当前主要关键词的实现难度、前置依赖和推荐落地顺序。

当前可用的原游戏解包参考目录：

- `E:\DATA\GODOT\MyMod\sts104`

当计划进入具体实现阶段时，可先对照该原版目录中的卡牌、能力、遗物、动作和 Hook 调用链，避免只凭印象复刻；但当前项目只面向 103 正式版，API 签名必须再以目标 103 游戏目录中的 `sts2.dll` 校验。

## 2. 当前关键词清单

当前关键词页列出的核心对象：

- `灵感`
- `黑云`
- `黑云姿态`
- `凝聚`
- `月影`
- `预见`
- `初始遗物`
- `雪`
- `月`
- `花`

其中前六项属于核心机制；`初始遗物` 是机制入口；`雪/月/花` 更接近后续联动能力层。

## 3. 难度判断

### 低难度

- `预见`
  - 原因：更像对原版现成行为的直接调用，主要风险在于卡牌描述、动作调用和数值。
  - 依赖：无特殊状态机。

- `初始遗物`
  - 原因：入口简单，只需要在战斗开始时触发一次 `凝聚1`。
  - 依赖：必须先有 `凝聚` 的稳定实现。

### 中等难度

- `凝聚`
  - 原因：需要操作手中的 `月影`，同时可能生成 `月影`，还涉及费用修改与重放次数。
  - 风险：手牌检索、生成卡牌、卡牌实例状态修改、描述同步。

- `黑云姿态`
  - 原因：本质上是玩家状态机，规则明确，但需要覆盖“进入”“保持”“退出”三个时点。
  - 风险：卡牌结算时机、攻击/非攻击判定、与黑云额外效果的连接方式。

### 中高难度

- `月影`
  - 原因：它不是单纯关键字，而是一张有成长值、保留、与其他攻击联动的 Token 卡。
  - 风险：卡实例上的动态伤害值、保留、命中后成长、被 `凝聚` 改写费用与重放。

- `雪 / 月 / 花`
  - 原因：它们互相授予额外关键字，并在三者齐备时移除 3 个能力再生成 `居合`。
  - 风险：不可叠加、跨能力联动、检测三件套、移除能力并生成奖励。

### 高难度

- `灵感`
  - 原因：规则不是“打出时触发”，而是“回合开始和普通抽牌以外，以其他方式把牌加入手中时，牌会解锁额外效果”。
  - 风险：
    - 需要识别“加入手牌”的来源
    - 需要区分“抽牌”与“非抽牌加入”
    - 需要决定灵感是作用在卡实例、当前事件，还是玩家临时状态
    - 许多卡牌都依赖这个判定，属于全局地基机制

- `黑云`
  - 原因：表面像条件分支，实际上绑定了 `黑云姿态` 的完整进入/退出循环。
  - 风险：
    - 需要统一卡牌侧 API
    - 需要保证“未在姿态中时进入姿态，在姿态中时吃到额外效果”
    - 与 `灵感`、`月影`、`花` 等后续联动有耦合

## 4. 推荐实现顺序

推荐不要按关键词页顺序做，而是按依赖闭环做：

1. `预见`
2. `月影` Token 最小版本
3. `凝聚`
4. `初始遗物`
5. `黑云姿态`
6. `黑云`
7. `灵感`
8. `雪 / 月 / 花`

这个顺序的原因：

- `预见` 最独立，适合作为第一批打通“卡牌 -> 动作 -> 文本”的验证样本。
- `月影` 和 `凝聚` 可以先形成一个比较封闭的小体系。
- `初始遗物` 在 `凝聚` 完成后几乎是顺手闭环。
- `黑云姿态` 必须先于 `黑云`。
- `灵感` 是全局判定层，适合在已有卡牌与状态样本后实现。
- `雪/月/花` 依赖多个核心机制稳定后再做，返工最少。

## 5. 关键词拆解与步骤

### 5.1 预见

目标：

- 能在卡牌结算中调用原版 `预见` 行为
- 能正确显示数值与描述

步骤：

1. 在 `sts104` 中定位原版使用 `预见` 的卡和动作。
2. 确认当前项目中调用动作的最小写法。
3. 先做一张只包含 `预见` 的测试牌。
4. 验证抽牌、弃牌、描述是否一致。

完成标志：

- 至少一张卡能稳定执行 `预见`
- 不额外引入 Yuki 自定义状态

### 5.2 月影

目标：

- 实现 `月影` Token 卡
- 支持 `0` 费、保留、基础伤害、随攻击命中成长

步骤：

1. 定义 `月影` Token 卡模型。
2. 决定“当前造成 x 点伤害”存放在卡实例还是外部能力中。
3. 实现“其他攻击命中时 +1 伤害”。
4. 处理保留与描述刷新。

风险点：

- 卡实例动态数值刷新
- 多张月影同时存在时的状态归属

完成标志：

- `月影` 可生成、可保留、可成长
- 描述与实际伤害一致

### 5.3 凝聚

目标：

- 优先处理手中已有 `月影`
- 没有 `月影` 时生成一张

步骤：

1. 实现“查找手中月影”的共用帮助函数。
2. 实现“月影费用 +1”。
3. 实现“获得重放 1”。
4. 没有月影时生成月影。
5. 将这套逻辑做成卡牌与遗物都能复用的服务方法。

风险点：

- “重放 1”应落在卡实例还是使用流程
- 费用调整持续到何时

完成标志：

- 一张 `凝聚` 牌和初始遗物都能调用同一套逻辑

### 5.4 初始遗物

目标：

- 战斗开始时 `凝聚1`

步骤：

1. 在 `YukiStarterRelic` 上补完整入口。
2. 调用 `凝聚` 的共用逻辑，而不是另写一套。
3. 补遗物文案与图标占位。

完成标志：

- 战斗开始稳定触发一次
- 与手中已有/没有月影两种情况都正常

### 5.5 黑云姿态

目标：

- 有统一的“是否处于黑云姿态”状态源
- 非攻击牌会退出姿态

步骤：

1. 先决定落地形式：推荐先做成 `Power`，不要先做复杂自定义姿态系统。
2. 实现“进入黑云姿态”与“退出黑云姿态”帮助方法。
3. 在打牌流程中拦截“使用的是否为攻击牌”。
4. 为调试期提供明显的图标/提示。

风险点：

- 需要找对打牌 Hook
- 要避免和未来正式姿态系统冲突

完成标志：

- 可被卡牌可靠进入
- 非攻击牌会可靠退出

### 5.6 黑云

目标：

- 统一“如果已在黑云姿态中，则吃额外效果；否则进入黑云姿态”的流程

步骤：

1. 给 `YukiModCard` 增加一个共用判断/包装入口。
2. 先用 2 到 3 张卡验证黑云基础分支。
3. 再扩展到额外攻击、额外抽牌、保留姿态等变体。

风险点：

- 如果每张卡自己写判断，后续容易发散
- 需要统一“黑云额外效果”的描述方式

完成标志：

- 至少有攻击牌、技能牌各一张共享同一个黑云判定入口

### 5.7 灵感

目标：

- 正确识别“非抽牌、非回合开始”的入手事件
- 为依赖灵感的卡提供统一判定

步骤：

1. 在 `sts104` 中先查原版所有“加到手牌”“抽牌”“回合开始进手牌”的动作路径。
2. 明确哪些事件算灵感，哪些不算。
3. 设计最小数据结构：
   - 候选 A：卡实例上挂 `IsInspired`
   - 候选 B：本次入手事件写入临时标记
   - 候选 C：玩家身上挂一层“本回合入手来源记录”
4. 先只支持 1 到 2 条明确来源，例如“生成到手牌”“弃牌堆回手牌”。
5. 用最依赖灵感的几张牌做回归。

风险点：

- 全局性最强，最容易返工
- 如果来源判定做粗，会导致大量误触发

完成标志：

- 有一套明确的“算灵感/不算灵感”判定表
- 至少两种入手来源被正确识别

### 5.8 雪 / 月 / 花

目标：

- 三个不可叠加能力互相授予额外效果
- 三者齐备时移除自身并生成 `居合`

步骤：

1. 明确它们是卡牌生成的 `Power` 还是特殊能力层。
2. 分别实现不可叠加。
3. 实现两两增益。
4. 最后实现“三件套检测 -> 移除三者 -> 生成居合”。

风险点：

- 能力移除顺序
- 多来源叠加与重复获得

完成标志：

- 三者单独存在时各自有效
- 三件套时只触发一次转化

## 6. 推荐的第一批落地闭环

建议不要先做 `灵感`，而是先完成这个最小可验证闭环：

1. `月影` Token
2. `凝聚`
3. `初始遗物`
4. 一张调用 `凝聚` 的技能牌

原因：

- 依赖集中
- 状态更容易观察
- 不需要先解决全局“入手来源”问题
- 可以较快验证卡牌、遗物、Token、动态数值四条链路

## 7. 暂不建议优先做的内容

- 一开始就做完整 `灵感`
- 一开始就做 `雪/月/花`
- 一开始就把 `黑云姿态` 扩展成重量级自定义姿态系统
- 一开始就同时铺大量依赖不同关键词的卡牌

这些都容易把当前还很空的工程拉进大范围返工。
